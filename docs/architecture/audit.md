# Engineering audit

## Scope and baseline

This audit inspected the manifest, lockfile, library exports, CLI, every Rust
module, repository history, ignored database samples, and current tests.
`Cargo.toml` declares package `passql`, Rust edition 2024, and no external
dependencies. `cargo test` initially ran 49 tests. The current working tree
has 71 after adding format inspection, B+ tree, and transaction tests.
Clippy, formatting, build, and documentation generation pass.

The sample files are local and ignored by `.gitignore`. Their signatures show
version 1, version 2, and version 3 files. They were not modified. Version 4
files are generated by tests and are not existing sample databases.

Severity describes risk in the current implementation, not an assessment of
the project's intended final design.

## Findings

| Severity | Affected components | Finding and evidence | Recommended solution |
|---|---|---|---|
| High | `src/storage.rs`, version 2 | The page count is updated in place at header offset 16. It has no checksum or alternate publication slot. `open` truncates any bytes after the committed count and takes no lock. Concurrent writers or a concurrent open during append can overwrite or truncate each other's data. | Stop using version 2 for concurrent writes. Keep compatibility reads explicit. Move new writes to a separately versioned design with locking and atomic publication, then add crash and concurrency tests. |
| High | `src/storage_v3.rs`, `src/transaction.rs` | Version 3 synchronizes appended pages before publishing a commit slot, which is a useful ordering step, but it does not prove atomic publication on all filesystems. Commit checksums cover commit metadata, not the referenced pages. Recovery selects the newest slot whose size fits, even if a page is corrupt. | State the filesystem assumptions and test failure boundaries. Add page checksums and an explicit recovery validation policy. Do not describe the current slots as a general durability guarantee. |
| High | formats 1, 2, 3, and 4 | Version 1 was supported in repository history, but current `Storage` accepts only version 2, `DatabaseReader` accepts only version 3, and `StorageV4` accepts only version 4. There is no migration utility. Local version 1 samples use uppercase `PASSQL` and lowercase `passql` signatures, while version 2 uses lowercase `passql` with version number 2. | Keep exact signature and version handling. Provide explicit read or export support before migration. Never silently rewrite a file. |
| High | `src/transaction.rs`, `src/storage_v3.rs` | Version 3 transactions stage append only records. They do not offer reads in a transaction, update, delete, index changes, or concurrent transaction isolation beyond one mutable handle. Version 4 adds staged reads and atomically publishes changed records and the index root, but does not reclaim old pages. | Keep the version specific APIs explicit. Extend version 4 failure testing and add reclamation only after snapshot lifetime is safe. |
| Medium | `src/kv.rs`, `src/transaction.rs`, `src/reader.rs` | Key lookup in versions 2 and 3 scans pages backward. Lookup cost grows with the full history, including older overwritten values. Version 4 now provides a separate persistent index. | Keep legacy APIs explicit. Benchmark version 4 against a scan, and avoid calling an index feature support for old formats. |
| Medium | `src/record.rs`, `src/reader.rs` | The record checksum is 32 bit FNV 1a over only the payload. The record type and length fields are not covered. Version 3's commit checksum is 64 bit FNV 1a and does not protect data pages. These checksums detect some accidental changes but are not cryptographic. | Specify checksum coverage in a new format and checksum the complete page envelope. Reject malformed headers before slicing. |
| Medium | `src/slotted.rs` | The slotted page is an in memory encoding. It has no checksum, is not wired to storage, does not reclaim deleted space, and appends new slots instead of reusing space. | Treat it as experimental. Add page integrity, compaction, slot reuse rules, and persistence tests before using it for durable records. |
| Medium | `src/storage_v3.rs`, `src/storage_v4.rs`, `src/reader.rs` | Version 3 uses operating system file locks. Version 4 locks writers and relies on immutable pages for unlocked reader snapshots. These assumptions depend on local file behavior. Version 2 uses no lock. Creation does not synchronize its parent directory entry. | Document supported operating systems and filesystem behavior. Add platform tests and parent directory durability handling where supported. |
| Medium | CLI and public APIs | The CLI mixes stable looking version 2 commands and experimental version 3 commands. `info` and `verify` originally assumed one version each, and there is no general database open operation. Error reporting is based mostly on `io::Error` strings. | Keep versioned commands explicit until the default is chosen. Make format recognition read only, standardize error context, and expose only functioning commands. |
| Medium | `.gitignore` and samples | `*.psl` ignores every sample database, including files useful for format compatibility testing. Local sample files are not reproducible from a clean clone. | Use generated test fixtures or carefully selected tracked fixtures with explicit ignore exceptions. Never remove local samples as cleanup. |
| Medium | `src/storage_v4.rs`, `src/btree.rs` | Version 4 implements an append only copy on write B+ tree and commits record references with the new root. It does not merge underfull nodes or reclaim old pages. Open validates the full tree, so startup is linear. Only prepublication and partial slot failures are injected in tests; real power loss and all filesystem behaviors remain untested. | Keep the format experimental. Add failure injection at each sync boundary, benchmark open and lookup, and design safe reclamation around live snapshots. |
| Low | SQL, documents, clients, editor support | There is no SQL parser, SQL execution, document API, TypeScript package, ORM adapter, VS Code extension, import or export, or benchmark suite. | Keep README and CLI claims limited to verified behavior. Add each layer after the storage contracts it depends on. |

## Architecture assessment

The repository is small and has no meaningful directory boundaries yet. Its
modules already separate some concerns, but `record.rs` adds methods directly
to version 2 `Storage`, while the newer formats have separate storage APIs.
Version 4 adds an index specific writer and reader rather than changing old
format behavior. Keep the formats distinct until an explicit common storage
contract can preserve their compatibility boundaries.

There is no unnecessary dependency or synchronization framework. The main
allocation costs are one page sized stack or heap buffer per operation, a
`Vec` of full pages while staging a version 3 transaction, and a newly
allocated `Vec` for each value read. These should be measured after a correct
index and transaction design exists.

## Recovery decision

Do not extend the current alternating commit slots by assumption. Their
checksums identify many torn metadata writes, and data is synchronized before
the new slot, but the code has no page checksum, no device level atomic write
assumption, no directory sync on creation, and no systematic power loss tests.
Version 4 uses copy on write because its pages are append only and the commit
publishes the root and page count together. This reduces the chance that an
index points at an unpublished record. It still does not prove durable
publication under arbitrary power loss or filesystems.

## Validation still needed

* Inject short writes and sync failures at each page and commit boundary.
* Simulate restart after every possible publication step.
* Test simultaneous processes, not only handles in one process.
* Test on each claimed operating system and filesystem.
* Test malformed headers, lengths, page references, slot counts, and checksum
  fields with fuzzing or property based tests.
* Add golden fixtures for every supported version and a non destructive
  compatibility test.
* Add an actual SQL parser, document API, and client integration only when
  those features are implemented and tested.
